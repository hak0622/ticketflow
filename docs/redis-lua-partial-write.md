# Redis Lua 부분 쓰기 보호

새 예매 요청은 기존 요청 해시에 inventoryVersion=1과 inventoryPhase를 기록한다. 선점 유효시간인 holdVersion=2와는 별개다.

| 작업 | 진행 중 | 완료 |
|---|---|---|
| 선점 | RESERVE_PENDING | HELD |
| 반환 | RELEASE_PENDING | RETURNED |
| 정상 매진 | 단일 쓰기 | SOLD_OUT |
| 미선점 종료 | 단일 쓰기 | NOT_HELD |

진행 표시는 첫 쓰기에 기록하고, 재고·활성 요청·입장권 처리가 끝난 마지막 쓰기에서 완료로 바꾼다. 진행 중이거나 새 형식이 손상되면 선점·조회·반환 Lua와 Java 매진 조회에서 차단한다. 정상 경로에 별도 Redis 왕복 조회를 추가하지 않는다. 추가 쓰기 비용의 부하 측정은 하지 않았다.

고정 코드 없는 Lua 실행 오류나 timeout도 성공/미실행으로 바꾸지 않는다. 기존 새 DB 잠금 조회와 복구 Worker가 저장 결과와 Redis 진행 표시를 재확인한다. 완료 후 응답 유실은 기존 결과를 재사용한다. 반환 도중 실패하면 예매 취소는 이미 커밋됐을 수 있지만 요청 반환 완료와 Outbox PUBLISHED는 기록하지 않는다.

두 필드가 없는 이전 형식은 기존 처리를 유지한다. 새 필드 하나만 있거나 미지원 버전·상태 조합은 보류한다. 두 필드가 함께 유실되는 손상은 이전 형식과 구분할 수 없다. 혼합 버전 실행은 지원하지 않으며 실제 적용 시 모든 앱을 중지하고 같은 버전으로 적용한다. 기존 시연 환경은 이번에 변경하지 않았다.

## 보류된 작업 확인

1. 요청 ID로 booking_attempt, 연결 Booking, 해당 Booking의 Payment와 Outbox를 조회한다.
2. 해당 Redis 요청 해시, 활성 선점 키, 입장권 키, 공연 재고와 오류 로그를 원본 보존한다. PG 키와 인증 정보는 공개하지 않는다.
3. 수동 판단·변경 전에 모든 앱의 쓰기를 중지하고 다시 스냅샷을 확보한다. 앱 중지가 이미 발생한 불일치를 복원하지는 않는다.
4. 진행 표시가 증명하는 사실과 증명하지 못하는 사실을 구분한다. RELEASE_PENDING만으로 INCR 전/후를 알 수 없고, 현재 수량과 과거 remaining 비교도 다른 사용자의 요청 때문에 근거가 되지 않는다.
5. 변경 여부를 입증하지 못하면 미해결·수동 확인 대상으로 유지한다. 재시작·Outbox 관리자 재시도는 진행 표시를 해제하지 않는다. 재고 덮어쓰기나 임의 완료 표시 변경을 하지 않는다.

예매 Worker는 기존 backoff로 재확인한다. Outbox는 기존 일반 오류 3회 후 FAILED·알림 정책을 유지하며, 미확정 결제 보호용 PaymentDeferredException과 구분한다. 자동 재고 보정, 새 관리 API나 DB 상태는 추가하지 않는다.

Redis 데이터/진행 표시 유실, 실제 OOM·Redis 프로세스 종료, 자동 재고 재구축은 보장하지 않는다. 명시적 Lua 오류 주입은 이 장애를 모두 재현한 것이 아니다.

## 검증

수정 전 실제 MySQL·Redis에서 차감 없는 예매 생성과 중복 반환 위험을 재현했다. 이는 안전성 통과가 아닌 기존 위험의 재현이다. 수정 후 각 쓰기 경계의 일반 실행 오류를 최초 한 번만 주입하고, 운영 Lua와 API·Worker·Outbox 경로로 재시도한다. 통과 기준은 이미 발생한 불일치의 복원이 아니라 추가 손상 방지다. 테스트는 주입 시점을 알고 있으므로 운영에서도 같은 수준의 관측이 가능하다고 주장하지 않는다.

최종 실행 ID: `20261112-190450`. 원본은 `test-results/redis-lua-partial-write/20261112-190450/`이며 Git 제외 로컬 자료다.

| 실행 | 건수 | 실패/오류/skip |
|---|---:|---|
| 수정 전 위험 재현 | 2 | 0/0/0 (위험 확인, 안전성 통과 아님) |
| 신규 보호 최종 검증 | 15 | 0/0/0 |
| 기존 선택 회귀 | 164 | 0/0/0 |

최종 보호·회귀는 총 179건 선택 실행이며 상속 반복 실행이 포함된다. 저장소 전체 테스트나 179개의 독립 장애 조합을 뜻하지 않는다. 기존 실제 Redis 선점/반환 응답 유실 회귀도 포함했다. 신규 테스트의 Worker·만료·Outbox 호출은 명시적 서비스 통합 검증이며 신규 다중 앱 자동 스케줄링 검증은 아니다.

첫 회귀 164건 중 1건은 이전 형식 fixture가 새 진행 표시를 남겨 손상된 새 형식으로 판정돼 실패했다. 운영 보호를 완화하지 않고, 해당 fixture에서 releaseOutcome과 새 필드 두 개를 제거해 실제 이전 형식으로 수정한 후 164건을 재실행해 통과했다. 초기 실패 로그·XML·진단과 예비 13건 실행은 별도로 보존하며 최종 건수에 중복 합산하지 않는다.

각 쓰기 경계 주입 Lua, DB/Redis after-fault·final 스냅샷, 명령·로그·XML·소스 해시를 보존했다. 정상 API의 고정 코드 없는 오류는 재확인 경로에서 보류된다. 관리자 재시도와 예약 만료·예매 Worker도 미완료 반환을 완료 처리하지 않음을 검증했다.

재현에는 Docker Desktop·Java 17·의존성 캐시가 필요하다. 신규 테스트는 `./gradlew test --offline --tests studying.blog.fault.RedisLuaPartialWriteIntegrationTest`로 실행한다. 이전 위험 재현은 LUA_BASELINE=true와 LUA_BASELINE_DIR에 보존된 이전 Lua 파일을 지정해야 하며 기본 실행에서는 비활성화된다. 이전 스크립트는 Git의 089688a 버전에서 확보할 수 있다. 테스트는 폐기 가능한 Testcontainers DB·Redis만 사용한다.

## 불완전 진행 기록의 관리자 알림

`InventoryObservation`은 별도 단일 실행기에서 30초마다 REQUESTED/RELEASE_PENDING 요청을 ID 순서로 100건씩 읽고 Redis primary의 요청 해시를 HMGET 합니다. 재시도 횟수·기한은 필터가 아닙니다. DB 조회 트랜잭션은 Redis 호출 전에 종료됩니다. 일반 재시도 실패가 아니라 `inventoryVersion=1`의 RESERVE_PENDING/RELEASE_PENDING만 집계합니다. 정상 Lua 실행 중에는 다른 연결의 HMGET이 끼어들지 못합니다.

전체 관측 성공 시에만 단계별 `booking_inventory_incomplete_current`와 `booking_inventory_observation_last_success_timestamp_seconds`를 갱신합니다. 최초 건수는 NaN, 성공 시각은 0입니다. 일부 조회 실패·기록 손상·소유자 불일치는 이전 결과를 유지하고 관측 오류 로그를 남깁니다. 관측기는 Redis·DB 업무 데이터를 수정하지 않습니다.

Prometheus는 최근 120초 이내 성공한 앱의 건수를 단계별 max로 집계하고 30초 지속 시 알립니다. 별도 감시 불가 규칙은 관측 성공 시각 만료, 앱 scrape 실패, 메트릭 누락, 대상 job 소실을 60초 지속 조건으로 감시합니다. 따라서 관측 실패 후 알림까지는 추가 평가·전달 지연이 있습니다. 여러 앱은 같은 DB·Redis를 공유한다는 전제이며 글로벌 스냅샷이 아닌 페이지 순회 관측입니다.

Slack 연결은 기존 `docs/payment-compensation-alerting.md` 설정을 사용합니다. 기존 Outbox FAILED 알림도 유지합니다. 업무 알림 해제만으로 문제 해결을 판단하지 말고 감시 불가 알림을 함께 확인하세요. 모니터링·Slack 자체의 장애는 외부 감시 대상이며 이번 구현에서 보장하지 않습니다.

관리자는 `[INVENTORY][INCOMPLETE]` 로그의 요청 ID로 위 운영 확인 절차를 진행합니다. Redis 상태 조회가 불가능하면 부분 쓰기로 단정하지 않습니다. 이전 형식, Redis 기록 유실, DB 후보와 연결되지 않은 고아 기록은 탐지 보장 대상이 아닙니다. 정상 응답 유실로 완료 표식이 남았다면 부분 쓰기 알림 대상이 아닙니다. 재고 수량을 수정하거나 진행 표시를 해제하는 관리 API·명령은 추가하지 않았습니다.

### 알림 검증 결과 (2026-11-12)

관측 관련 19실행(실제 MySQL/Redis 기반 18실행, 장애 모의 단위 1실행)과 기존 예매·반환 장애 회귀 48실행이 통과했습니다. 상속으로 기존 사례를 재실행한 건수를 포함하며, 서로 다른 장애 67종이라는 뜻은 아닙니다. 정상 Lua 실행 중 다른 연결의 조회가 대기했다가 완료 상태를 읽는 테스트도 통과했습니다.

promtool 5개 시나리오에서 발화·해제·다중 앱 집계·오래된 결과 제외·scrape 실패·메트릭 누락·job 소실을 확인했습니다. 격리된 Prometheus/Alertmanager와 로컬 수신 서버로 발화·해제 전달에 성공했습니다. 첫 시험은 수신 서버의 성공 응답이 Slack Incoming Webhook 규약과 달라 해제 전달에 실패했으며, 원본을 보존하고 시험 서버를 수정했습니다.

실제 Slack 발송, 앱 3대 실프로세스, 관측기의 자동 30초 주기 장시간 시험, 실제 Redis 연결 중단 후 관측기 복귀는 미검증입니다. DB·Redis 오류 시 스냅샷 유지는 단위 모의 테스트이며, Redis 손상 기록으로 관측 실패 시 기존 결과 유지는 실제 통합 테스트입니다. 기존 응답 유실 회귀는 포함하지만 관측기와 통신 차단 프록시를 결합한 추가 시험은 하지 않았습니다. k6·실제 Toss·재배포·커밋·푸시는 수행하지 않았습니다.

원본은 Git 제외 경로 `test-results/inventory-alerting/20261112-203654/`에 보존했습니다. 규칙 시험은 `prometheus/tests/inventory-observation.yml`, 로컬 전달 시험은 `python3 perf/inventory_alert_delivery.py`로 재현합니다. 전달 시험은 전용 컨테이너·네트워크만 생성·삭제하고 기존 환경은 조작하지 않습니다. 결과는 `test-results/inventory-alerting/current/`에 저장됩니다.

### 후속 실제 Slack 전달 시험 (2026-11-12)

사용자의 실제 발송 요청에 따라 기존 Webhook으로 ‘Lua 부분 쓰기 알림 연결 시험’ 발생·해제 두 메시지를 보냈습니다. 격리된 Prometheus/Alertmanager의 시험 지표를 사용하고 로컬 전달 서버가 실제 Slack Webhook으로 전달했으며, 두 요청 모두 HTTP 200 / `ok`를 받았습니다. 채널 화면에서의 열람 확인이나 시연 앱 재배포를 의미하지 않습니다. 앞 절의 실제 Slack 미실행 표기는 최초 시험 당시 범위이며, 이번 후속 시험에서 전달 확인을 추가했습니다. 원본은 Git 제외 경로 `test-results/inventory-alerting/actual-slack-20261112-204042/`에 보존했습니다. 시험 컨테이너·네트워크는 정리했고 시연 데이터는 변경하지 않았습니다.

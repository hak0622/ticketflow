# 1·2단계 최적화 후 k6 재측정 결과

> 이 문서는 작성·실행 당시의 계획 또는 검증 기록입니다. 현재 흐름은 [문서 안내](README.md), PG 구현 및 한계는 [결제 결과](payment-saga-results.md)를 확인하세요. 과거 결과는 현재 전체 기능의 검증을 뜻하지 않습니다.

**27회 모두 통과했다. 현재 버전의 300석 평균 지연은 복구 추가 직후보다 줄었지만 500석과 대기열 전체 흐름은 늘었다. 성능이 전반적으로 회복됐다고 판단하기 어렵다. 이번 세 버전 모두 커넥션 획득 타임아웃은 0건이다.**

## 환경과 비교 방법

2026-11-04 KST, 실행 ID `20261104-123822-fce4d1`. 과거 실행 `20261103-221647-78d9fd`에 보존된 baseline/current JAR를 각각 baseline/recovery로 재실행했다. SHA-256이 원본 메타데이터와 같은지 검증했다. current는 최적화 작업 트리를 빌드했다.

- Docker Desktop 29.3.1, VM 10 CPU/8,217,059,328 bytes. 이전 실행과 같다. MySQL/Redis/Temurin/k6 이미지 digest도 모두 같다.
- 앱 1대, 2 CPU/1GiB, Java 17, heap 512MiB. MySQL 8.4 2 CPU/1GiB, Redis 7-alpine 1 CPU/256MiB, k6 1.0.0 2 CPU/2GiB.
- Hikari 최대 20, 획득 제한 3,000ms. Tomcat worker 최대 100. P6Spy OFF, 서비스 기본 INFO/WARN 로그.
- 각 버전 워밍업 20 VU×25회, 서로 다른 사용자 500명. 본 측정은 500 VU×1회, API 500석/API 300석/대기열 500석을 순서대로 3회 반복했다.
- 본 측정 예매 POST 13,500회. 워밍업 1,500회를 별도 보존했다. 예매 재시도는 수행하지 않았다. 대기열은 1초/100명, 입장권 600초, 기존 adaptive polling/jitter와 JWT 발급 방식을 사용했다.
- 측정 중 예매 소스·풀 설정 변경 없음. src/main 전체 해시가 시작 시점과 끝 시점에 같은 것을 확인했다. 기존 compose.yml 리소스 설정을 사용했다.
- 버전별 전용 DB/Redis/볼륨을 사용하고 종료 후 컨테이너·볼륨 삭제를 확인했다. 기존 로컬/프로덕션 데이터는 사용하지 않았다.

같은 머신에서 baseline→recovery→current 순서로 실행했다. 호스트를 독점하지 않았고 난수 jitter 및 JIT/스케줄링 변동이 있다. 세 번의 중앙값은 통계적 유의성을 증명하지 않는다.

## 현재 버전의 변화율

지연 시간의 +는 증가, -는 감소다. TPS의 +는 증가다.

| 조건 | 비교 대상 | API 평균 변화 | API p95 변화 | 전체 흐름 평균 변화 | 응답 TPS 변화 |
|---|---|---:|---:|---:|---:|
| api/500 | 기존 Redis Lua | +101.13% | +92.58% | +101.53% | -46.37% |
| api/500 | 복구 추가 직후 | +21.73% | +11.99% | +26.18% | -11.72% |

| api/300 | 복구 추가 직후 | -9.15% | -10.05% | -4.94% | +7.53% |
| flow/500 | 기존 Redis Lua | +141.26% | +48.77% | +13.36% | -9.20% |

500석 API 평균은 복구 추가 직후보다 약 21.7% 증가했고 기존 Lua보다 약 101.1% 증가했다. 300석은 복구 추가 직후보다 약 9.2% 감소했지만 기존 Lua보다 약 54.4% 증가했다. 대기열 전체 흐름 평균은 복구 추가 직후보다 약 4.0% 증가했다. 300석 경로에서 일부 개선이 관측됐으며 성공 경로는 추가 개선이 필요하다.

## Hikari와 타임아웃

active 평균은 회차별 샘플 평균의 중앙값이며 시간 가중 사용률은 아니다. peak는 3회에서 관측한 최댓값이다. nominal 수집 간격은 100ms지만 scrape 응답 시간이 추가된다. timeout은 burst 앞뒤의 모니터 구간에서 누적 카운터 차이를 구하고 앱 오류 로그로 재확인했다.

과거 3단계의 복구 버전 300석 1회차는 타임아웃 1건이 있었다. 이번 현재 버전에서는 재현되지 않았다. 이번 복구 추가 직후 버전도 타임아웃이 0건이므로 최적화가 타임아웃 원인을 해결했다고 확정할 수 없다. 현재도 active 20/pending 최대 81에 도달해 커넥션 대기가 남는다.

500석 API 모니터 구간의 커넥션 획득 횟수는 복구 버전 533~536회, 현재 1,033~1,035회였다. 현재는 OSIV를 끄고 트랜잭션마다 반환·재획득하므로 획득 횟수 증가와 일치한다. 이 카운터에는 백그라운드 조회가 포함돼 요청별 정확한 횟수로 해석하지 않는다. 이번 테스트는 개별 SQL/COMMIT 시간을 계측하지 않았으므로 지연 증가 전부를 OSIV나 단일 SQL 원인으로 돌릴 수 없다.

## 정합성

- 모든 27회에서 잔여석 0, 초과 예매·사용자 중복 Booking·수량 불일치 없음.
- 각 버전 500석 API/대기열은 매번 Booking 500건이다. 복구 버전과 현재는 BOOKED 요청 500건, 미완료 0건이다.
- 300석은 매번 Booking 300건/정상 매진 200건이다. 복구 버전은 BOOKED 300/RELEASED 200, 현재는 BOOKED 300/REJECTED 200이다.
- 현재 REJECTED는 result_status=SOLD_OUT, Redis RELEASED/result=SOLD_OUT, 소유자 일치, 선점 이력 및 활성 사용자 표식 없음까지 확인했다.
- Booking↔attempt 연결 및 요청별 Redis 표식 검사 이상 0건. 기준 Lua 버전은 booking_attempt 테이블이 없어 해당 검사 N/A다.
- 요청 500건이 종료되고 미완료가 없음을 5초 간격 두 번 확인했다. 테스트는 정상 부하이며 실제 반환/취소 부하의 성능은 별도 측정이 필요하다.

## 이전 기록과의 관계

과거 3단계 기록을 덮어쓰지 않았다. 과거 현재(복구) 500석 평균 1,855.87ms와 이번 최적화 1,515.92ms를 단순 비교하면 약 18.3% 감소다. 그러나 동일 JAR의 이번 복구 버전 평균도 1,245.30ms로 달라졌다. 회복 판단은 이번에 함께 재실행한 세 버전 결과를 기준으로 했다. 과거 비관적 락 3,778ms 및 이력서 수치와는 실행 조건 일치를 확인할 수 없어 직접 비교하지 않는다.

## 추가 개선 판단

성공 경로의 성능 개선이 필요하다. 우선 REQUESTED 커밋과 예매 트랜잭션 각각의 커넥션 획득 대기/보유 시간, SQL, COMMIT 시간을 분리 계측해 성공 경로의 병목을 좁혀야 한다. 요청 기록 선커밋·멱등성·Worker 잠금 보장을 유지하며 개선 대상을 선택해야 한다. 풀 크기와 timeout은 이번 측정에서 고정했다.

300석 감소만으로 1단계와 2단계 각각의 효과를 분리할 수 없다. 이번 부하는 실제 예약 취소/결제 보상의 반환 후처리 비용을 측정하지 않았다. 지속 부하·다중 앱·더 높은 동시성에서의 timeout 해결 여부도 미검증이다.

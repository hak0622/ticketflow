## 목적과 테스트 조건

- 로컬 앱 3개가 공유 MySQL 8.4·Redis 7을 사용하는 환경. 앱마다 1 CPU / 메모리 768MiB / heap 384MiB, Hikari 20개 / 획득 timeout 3초.
- 300명/300석과 500명/500석을 각각 독립 환경에서 실행. 실제 JWT·입장권·HTTP 예매 API와 실제 DB/Redis 사용. 대기열·PG는 제외했다.
- 각 사용자의 첫 요청은 앱 3개에 직접 분배한다. 초기 70%는 burst, 나머지 30%는 20~40초에 분산해 Worker 복구 시간대에도 예매를 계속한다.
- 지정한 요청이 앱 1에서 실제 Redis 선점을 마친 뒤 정지한다. 앱 2의 다른 요청도 실제 Redis 선점 후 DB 트랜잭션을 열어 둔다. 두 경계가 확인되면 앱 1을 SIGKILL하고 앱 2 요청을 재개한다.
- 초기 요청의 연결 오류·202 등은 동일 UUID로 생존 앱 2·3에 재시도한다. 지정한 장애 요청만 첫 연결 실패 후 40초간 기다려 자동 Worker가 먼저 반환하도록 한다.
- REQUESTED 유예 30초, Worker fixedDelay 5초, 트랜잭션 timeout 10초를 유지한다. DB 시각을 앞당기거나 Worker를 직접 호출하지 않았다.
- 각 조건은 워밍업 없는 1회 장애 시나리오다. **300/500명 전체가 종료 순간 동시에 처리 중이었다는 의미는 아니다.** 다른 앱의 실제 열린 트랜잭션 하나와 종료 시점의 중첩을 확정했다.

장애 요청 1건은 의도적으로 실패 종료·반환하므로 N-1건 예매 / 잔여 1장이 기대 결과다.
유예는 REQUESTED 생성 시점부터 계산되므로 선점 이후 관측한 복구 시간이 30초보다 짧을 수 있다.
이 시간은 저수준 이벤트의 이번 단일 실행 관측값이며 SLA/p95가 아니다.

검증한 조건:

1. 모든 사용자와 원래 UUID가 정확히 하나의 요청으로 연결된다.
2. Redis 잔여석 + 유효 Booking = 전체 수량이며 중복·초과 예매가 없다.
3. 성공 요청은 실제 Booking과 연결되고 Redis HELD / 활성 요청 키 / 입장권 소비 상태가 일치한다.
4. 장애 요청은 DB RELEASED / BOOKING_FAILED, Redis RELEASED / RETURNED, 활성 요청 키 없음, 입장권 존재로 일치한다.
5. 생존 앱 두 곳에 장애 요청을 3회 재시도해도 HTTP 409 / BOOKING_FAILED를 재사용하고 수량·요청·입장권 상태가 바뀌지 않는다.
6. 앱 1의 실제 SIGKILL 종료 코드 137 / OOMKilled=false를 확인했다. 실제 다른 앱의 열린 DB 트랜잭션이 종료 시점 이후 정상 커밋했다.
7. Worker는 자동 스케줄러에서 실행됐으며, 복구 시간대에 다른 예매 트래픽이 있었다. 정확히 같은 순간에 DB 문장 두 개가 실행됐다는 별도의 증명은 아니다.

## 응답 시간과 오류

| 지표 | 300명 | 500명 |

| 사용자 완료 수/위 구간 초 | 7.08 | 9.25 |

| 연결 오류 / 전체 POST | 9.37% | 14.53% |
| HTTP 5xx 응답 | 0 | 0 |
| 최종 예상 밖 사용자 실패 | 0 | 0 |

POST HTTP duration은 k6의 요청 timing 값으로, 실패한 연결의 전체 대기와 재시도 간 대기를 모두 포함하지 않는다.
사용자 시간은 첫 POST 직전부터 최종 결과까지로 재시도·연결 대기·장애 요청의 의도적인 40초 대기도 포함한다.
분산 유입을 위한 최초 20~40초 sleep은 사용자 시간에서 제외한다.
완료 사용자/초는 이 시나리오 전체 구간의 관측값이며 최대 TPS가 아니다.

**500명 조건의 사용자 p95 약 21.3초는 남은 사용자 경험 문제다.**
연결 오류 85건의 실제 메시지는 EOF 35건, no route to host 42건, dial i/o timeout 8건이다.
연결·재시도 지연이 사용자 시간에 포함됐지만 각 원인별 순수 대기 시간을 독립 계측하지는 않았다.
이번 클라이언트는 종료 후에도 일부 첫 요청을 앱 1에 직접 보내며, 실패한 뒤 생존 앱을 명시적으로 선택한다.
따라서 이 오류율을 실제 로드밸런서의 자동 우회 성능이나 운영 오류율로 해석하면 안 된다.
원래 요청의 연결 유실은 숨기지 않았으며, 재시도 후 정합성 통과와 HTTP 무오류를 구분했다.

## Hikari·자원

아래 순서는 앱 1 / 앱 2 / 앱 3이다. 각 peak는 서로 다른 시점의 표본이므로 합산하지 않는다.

| 항목 | 300명 | 500명 |
|---|---|---|
| 관측 active peak | 11 / 9 / 15 | 20 / 20 / 20 |
| 관측 pending peak | 0 / 0 / 43 | 57 / 58 / 59 |
| 수집 구간 timeout 카운터 증가 | 0 / 0 / 0 | 0 / 0 / 0 |
| 보존된 앱 로그의 획득 timeout 메시지 | 0 | 0 |

앱 1은 종료 직전 마지막 성공 scrape 이후 지표를 읽을 수 없다. 따라서 종료 순간까지의 카운터를 완전하게 관측했다고 주장하지 않는다.
생존 앱의 관측된 timeout은 0이지만 pending이 남아 있으므로 커넥션 대기 해소를 의미하지 않는다.
측정 시 호스트 swap 사용은 약 2.8GiB였고 Docker/호스트 자원 시계열을 함께 저장했다.
테스트용 Probe의 이벤트 파일·로그 기록 비용도 존재한다. 기존 정상 burst 결과와 성능 개선율을 계산하지 않았다.

## 초기 실행의 한계와 보완

`20261108-155010-c5b8b9` 두 조건은 수량·연결·자동 복구 검증을 통과했다.
다만 종료 전 여러 상태 조회를 하는 동안 다른 초반 요청이 끝나서, 다른 요청의 HTTP 구간과 종료 시점 중첩을 원본에서 확인하지 못했다.
이를 최종 부하 중 동시 실행 증거로 사용하지 않았다. `scope-verification.json`에 이 한계를 추가하고 원본을 유지했다.

보완 실행에서는 느린 종료 전 상태 조회를 제거하고 앱 2의 실제 예매 트랜잭션을 테스트 경계에서 잠시 유지했다.
서버 이벤트로 그 트랜잭션이 종료 순간 열려 있었으며 종료 후 정상 커밋됐음을 필수 검증했다.
예매·복구 운영 코드의 수정은 없었다.

## 남은 범위

이번 검증은 40초에 걸친 혼합 burst/분산 부하와 단일 앱 종료이다. 지속적으로 높은 예매 부하가 유지되는 상태,
1만 명/5분 대기열, 실제 LB 자동 장애 우회, 장시간 복구 backlog, Redis 유실/failover, MySQL 장애, 실제 PG 부분 실패는 별도 범위다.
기존 장애·만료·결제 보상 회귀 전체 묶음은 이번에 재실행하지 않았다.
다음에는 생존 앱으로의 자동 우회와 대기열 전체 입장량을 확인하면 사용자 연결 지연과 DB 유입 제어를 평가할 수 있다.
